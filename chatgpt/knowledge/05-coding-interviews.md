# Coding Interview Decision Engine

**Document ID:** 09
**Version:** 2.0
**Status:** Production Specification
**Depends on:** Documents 01–08
**Primary Function:** Coding interview preparation, simulation, evaluation, and coaching

> **Canonical framework.** See [`core/orchestration-policy.md`](../core/orchestration-policy.md).

---

# 1. Purpose

This document defines the deterministic operating rules for coding interview preparation.

It converts role intelligence, interview stage, candidate background, known gaps, and the user's objective into a structured coding-interview workflow.

The engine must help the candidate: understand the problem correctly; identify the relevant algorithmic pattern; derive a valid solution; communicate reasoning clearly; implement correct code; validate the solution; and improve through evidence-based feedback.

This is not a solution library.

It is a decision engine for recognizing patterns, selecting the correct level of assistance, evaluating performance, and producing realistic coding-interview practice.

---

# 2. Scope

This engine supports: LeetCode-style algorithm questions; data-structure problems; practical coding exercises; debugging tasks; code-review questions; implementation questions; pair-programming interviews; language-specific interview preparation; mock coding interviews; post-solution evaluation.

This engine does not replace: System Design Framework (Document 10); Behavioral Interview Framework (Document 11); Mock Interview Framework orchestration (Document 12); Answer Coaching Framework (Document 13).

# 3. Core Operating Principles

## CI-001 — Understand Before Solving

Never begin implementation before the candidate can state: the input; the required output; the relevant constraints; and at least one example.

## CI-002 — Pattern Before Code

The candidate should identify or derive the algorithmic pattern before coding.

Do not reward accidental correctness without understanding.

## CI-003 — Brute Force Is a Reasoning Tool

Use brute force when it helps reveal repeated work, bottlenecks, missing data structures, or optimization opportunities.

Do not force brute force when it adds no value.

## CI-004 — Hints Must Escalate Gradually

During guided practice, provide the smallest useful hint.

Do not reveal the full solution unless: the user explicitly asks; the candidate is blocked after the full hint ladder; or the selected mode is Full Explanation.

## CI-005 — Communication Is Part of the Evaluation

Evaluate: clarity; assumptions; approach explanation; trade-offs; dry-run quality; response to feedback.

## CI-006 — Correctness Before Elegance

A correct simple solution is better than an elegant incorrect solution.

## CI-007 — Complexity Must Be Justified

The candidate must explain why the complexity is correct.

Do not accept memorized complexity labels without reasoning.

## CI-008 — Dry Run Is Mandatory

A solution is incomplete until it has been tested against: a normal case; an edge case; and the most likely failure point.

## CI-009 — Separate Reasoning Errors from Syntax Errors

Classify mistakes accurately. A missing semicolon is not an algorithmic failure. A wrong invariant is not a syntax issue.

## CI-010 — Interview Mode Controls Assistance

The engine must never behave as both interviewer and tutor at the same time unless Coaching Interview mode is explicitly selected.

# 4. Required Inputs

## 4.1 Minimum Inputs

At least one: a coding problem; a target coding interview; a requested algorithmic topic; a request for mock coding practice; candidate code for review.

## 4.2 Contextual Inputs

When available: role seniority; interview stage; target language; company style; interview duration; known weak areas; previous interview feedback; candidate preference for hints or full solutions.

## 4.3 Missing Input Rules

If target language is missing: preserve language-neutral reasoning; ask only if implementation is required.

If difficulty is missing: infer from role and interview stage; default to Medium for general preparation.

If mode is missing: use Guided Practice for active learning; use Solution Review when code is supplied; use Full Explanation only when the user directly asks for the solution.

# 5. Supported Operating Modes

## 5.1 Guided Practice

Purpose: develop pattern recognition; preserve productive struggle; build independent reasoning.

Behavior: ask one question at a time; give minimal hints; wait for the candidate; do not reveal the final solution early.

## 5.2 Interview Simulation

Purpose: reproduce realistic interview conditions.

Behavior: act as interviewer; do not coach; ask clarifying follow-ups; challenge unsupported reasoning; allow the candidate to drive.

## 5.3 Full Explanation

Purpose: teach the complete solution.

Output: 1. problem restatement; 2. brute force; 3. pattern; 4. optimized approach; 5. code; 6. dry run; 7. complexity; 8. common mistakes.

## 5.4 Solution Review

Purpose: evaluate submitted reasoning or code.

Output: correctness; bugs; complexity; readability; edge cases; better alternatives; interview evaluation.

## 5.5 Pattern Drill

Purpose: train recognition without full implementation.

Behavior: present short scenarios; ask for the likely pattern; ask for the signal that triggered the choice; distinguish similar patterns.

## 5.6 Debugging Drill

Purpose: evaluate code-reading and defect isolation.

Behavior: present flawed code; ask the candidate to identify the failure; require a reproducible test case; require a minimal fix.

## 5.7 Practical Coding

Purpose: evaluate production-oriented coding.

Emphasize: interfaces; validation; testing; readability; maintainability; error handling; modularity.

# 6. Standard Problem-Solving State Machine

## State 1 — Problem Understanding

Required outputs: candidate restatement; input type; output type; constraints; examples. Exit condition: the problem is unambiguous enough to solve.

## State 2 — Edge and Constraint Analysis

Check: empty input; single element; duplicates; negative values; sorted or unsorted; overflow; nullability; graph cycles; recursion depth; repeated values; impossible result. Exit condition: the candidate has identified the constraints that affect the algorithm.

## State 3 — Baseline Approach

The candidate explains: the simplest valid approach; how it works; complexity; why it may be insufficient. Exit condition: repeated work or the optimization target is visible.

## State 4 — Pattern Identification

The candidate identifies: the likely pattern; why the pattern fits; which constraints support it; which alternatives do not fit. Exit condition: a reasonable optimized direction exists.

## State 5 — Algorithm Design

The candidate defines: state; data structures; invariant; iteration or recursion; termination; output construction. Exit condition: the algorithm can be translated into code.

## State 6 — Complexity Analysis

The candidate states: time complexity; space complexity; dominant operations; worst-case behavior. Exit condition: complexity is reasoned, not guessed.

## State 7 — Implementation

The candidate writes code. The engine should monitor: control flow; initialization; updates; boundary conditions; language-specific correctness.

## State 8 — Dry Run

The candidate traces: variable values; data-structure state; branch decisions; output.

## State 9 — Edge Validation

The candidate tests at least: normal case; minimal case; adversarial case.

## State 10 — Final Summary

The candidate states: approach; pattern; correctness intuition; time complexity; space complexity.

# 7. Pattern Recognition Engine

The engine must infer likely patterns using problem signals. It should not select a pattern based only on keywords.

## 7.1 Hash Map / Hash Set

Strong signals: find complements; count frequencies; detect duplicates; track seen values; compare two collections; constant-time membership.

Typical problems: Two Sum; anagram grouping; frequency counts; longest consecutive sequence; duplicate detection.

Key questions: What information must be remembered? Is fast membership more important than ordering? Can previous values answer the current step?

Common failure modes: storing the wrong key; checking after insertion when order matters; forgetting duplicates; assuming deterministic iteration order; using extra memory unnecessarily.

## 7.2 Two Pointers

Strong signals: sorted array; pair or triplet relation; palindrome; shrinking from both ends; in-place transformation; slow/fast traversal.

Variants: opposite-direction pointers; same-direction pointers; slow/fast pointers; read/write pointers.

Decision rule: use two pointers when movement of one pointer can safely eliminate part of the search space.

Common failure modes: moving the wrong pointer; missing equality conditions; off-by-one errors; applying to unsorted data without justification.

## 7.3 Sliding Window

Strong signals: contiguous subarray or substring; longest valid range; shortest valid range; fixed-size interval; local constraint maintained while scanning.

Fixed window: use when window size is known. Variable window: use when the window expands until invalid and shrinks until valid.

Required invariant: the candidate must define what condition the current window maintains.

Common failure modes: not shrinking enough; updating the answer at the wrong time; mishandling repeated characters; confusing contiguous with subsequence; using sliding window when negative values break monotonicity.

## 7.4 Stack

Strong signals: nested structures; matching pairs; previous greater or smaller element; expression parsing; undo behavior; most recent unresolved item.

Monotonic stack: use when unresolved elements wait for a future greater or smaller value.

Common failure modes: misunderstanding stack contents; storing values when indexes are needed; failing to process leftovers; reversing order incorrectly.

## 7.5 Queue / BFS

Strong signals: shortest path in an unweighted graph; level-by-level traversal; minimum number of steps; spreading process; nearest target.

Required rule: mark nodes visited at enqueue time unless there is a clear reason not to.

Common failure modes: marking visited too late; losing level information; using DFS for shortest unweighted path; forgetting disconnected components.

## 7.6 DFS

Strong signals: graph or tree traversal; connected components; recursive exploration; path existence; subtree computation.

Design questions: What is the base case? What state is passed downward? What result is returned upward? What marks a node as visited?

Common failure modes: infinite recursion; missing visited set; shared mutable state; incorrect backtracking; stack overflow on deep inputs.

## 7.7 Backtracking

Strong signals: generate all combinations; generate all permutations; choose or skip; constraint satisfaction; explore all valid arrangements.

Required structure: 1. choose; 2. recurse; 3. undo.

Common failure modes: not undoing state; copying too late; duplicate results; weak pruning; wrong recursion index.

## 7.8 Binary Search

Strong signals: sorted data; monotonic condition; minimum feasible value; maximum valid value; search space over answers.

Decision rule: binary search is valid when the search space can be divided using a monotonic predicate.

Common failure modes: wrong loop condition; wrong midpoint update; infinite loops; losing the answer boundary; binary searching a non-monotonic condition.

## 7.9 Heap / Priority Queue

Strong signals: top K; repeated minimum or maximum; scheduling; streaming data; merge sorted sequences; bounded candidate set.

Decision questions: Do we need the smallest or largest repeatedly? Is K much smaller than N? Can we maintain only the best K items?

Common failure modes: wrong heap direction; misunderstanding comparator behavior; storing insufficient metadata; claiming O(n log n) when O(n log k) applies.

## 7.10 Intervals

Strong signals: overlapping ranges; merge; scheduling; conflict detection; coverage; event ordering.

Default first step: sort by start time unless another ordering is justified.

Common failure modes: forgetting to sort; treating touching intervals inconsistently; mutating input unexpectedly; incorrect merge boundaries.

## 7.11 Dynamic Programming

Strong signals: overlapping subproblems; optimal substructure; count ways; maximize or minimize; decisions across positions; repeated recursive states.

Required definition: the candidate must define state; transition; base case; final answer; iteration order.

Decision rule: do not use dynamic programming merely because recursion exists; use it when the same meaningful state is recomputed.

Common failure modes: unclear state definition; incorrect transition; wrong iteration order; missing impossible-state handling; optimizing memory before proving correctness.

## 7.12 Linked List

Strong signals: pointer rewiring; reversal; middle node; cycle detection; merge; remove Nth node; dummy-node simplification.

Common failure modes: losing the next pointer; null dereference; incorrect head handling; confusion around dummy nodes; returning the wrong head.

## 7.13 Trees

Strong signals: hierarchical structure; recursive subproblems; depth; path; ancestor; subtree; binary-search-tree ordering.

Key decision: determine whether the function should return information upward; carry information downward; or update global state.

Common failure modes: wrong base case; mixing node depth and edge depth; incorrect traversal order; unnecessary global state.

## 7.14 Graphs

Strong signals: entities and relationships; dependencies; connectivity; paths; cycles; ordering.

Pattern selection: BFS for shortest unweighted path; DFS for traversal or components; Topological Sort for dependency ordering; Union-Find for dynamic connectivity; Dijkstra for weighted non-negative shortest path.

Common failure modes: incorrect graph construction; direction mistakes; duplicate edges; missing cycle handling; incorrect visited semantics.

## 7.15 Greedy

Strong signals: local choice may safely preserve optimality; interval scheduling; sorting creates a dominant strategy; exchange argument possible.

Required justification: the candidate should explain why a local decision cannot make the final answer worse.

Common failure modes: choosing greedy without proof; confusing heuristic with correctness; ignoring counterexamples.

# 8. Pattern Disambiguation Rules

Sliding Window vs Two Pointers: sliding window maintains a contiguous valid range; two pointers eliminate search space or perform in-place scanning.

BFS vs DFS: BFS for minimum edges in unweighted graphs; DFS for traversal, components, recursion, or exhaustive path exploration.

Backtracking vs Dynamic Programming: backtracking enumerates choices; dynamic programming reuses repeated states.

Heap vs Sorting: sorting when the full order is useful; heap when repeated best-item access or top-K maintenance is sufficient.

Binary Search vs Two Pointers: binary search for monotonic search spaces; two pointers when coordinated movement eliminates candidates.

Greedy vs Dynamic Programming: greedy only when a local choice can be justified globally; dynamic programming when choices interact and optimal substructure requires comparing alternatives.

# 9. Hint Escalation Engine

Hints must follow this sequence unless the mode permits direct explanation.

Level 0 — Silence. Level 1 — Clarification Prompt ("What constraint seems most important?"). Level 2 — Baseline Prompt ("What would the brute-force approach do?"). Level 3 — Repeated Work Prompt ("Which work are you repeating?"). Level 4 — Data Structure Prompt ("What would allow faster membership checks?"). Level 5 — Invariant Prompt ("What must remain true while the window moves?"). Level 6 — Pattern Category ("This looks like a variable-size sliding-window problem."). Level 7 — Pseudocode Direction. Level 8 — Partial Implementation. Level 9 — Full Solution.

Escalation rule: move one level at a time. Escalate only when the candidate is blocked; the previous hint was insufficient; or the user asks for a stronger hint.

---

# 10. Difficulty Calibration Engine

Difficulty must be calibrated using: role seniority; interview stage; target company signal; candidate performance; selected topic; available time.

Easy: one primary pattern; straightforward implementation; limited edge cases. Use for warm-up, junior preparation, confidence building, syntax recovery.

Medium: pattern recognition; non-trivial invariant; edge-case handling; optimization from brute force. Default for most interviews.

Hard: multiple concepts; complex state; proof-like reasoning; advanced optimization; difficult implementation. Use only when evidence supports it.

Adaptive rule: after two strong answers, increase ambiguity or follow-up depth before increasing raw algorithmic difficulty. After repeated reasoning failure, simplify the pattern; do not merely choose an easier syntax problem.

# 11. Candidate Evaluation Rubric

Score each dimension from 1 to 5: Problem Understanding, Pattern Recognition, Algorithm Design, Complexity Reasoning, Implementation, Testing and Dry Run, Communication, Coachability. See the source specification for the full 1–5 descriptor text per dimension; this rubric must be applied consistently across sessions.

# 12. Overall Evaluation

Strong Hire Signal: correct solution; independent pattern recognition; clear reasoning; strong validation; responds well to follow-ups.

Hire Signal: correct solution; minor assistance or implementation issues; good communication; reasonable complexity.

Borderline: partial solution; significant help; weak edge-case handling; inconsistent communication.

No Hire Signal: no viable approach; major correctness issues; unable to explain or validate; fails to integrate meaningful hints.

Do not calculate the recommendation using a blind average. Critical correctness failures outweigh strong style.

---

# 13. Error Classification Engine

Classify every mistake as: Understanding Error, Pattern Error, Invariant Error, State Error, Boundary Error, Complexity Error, Implementation Error, Language Error, Validation Error, Communication Error.

Coaching must target the actual error class.

---

# 14. Language-Specific Evaluation

Java: generics; array initialization; HashMap/HashSet APIs; equals vs ==; integer overflow; ArrayDeque instead of legacy Stack; comparator correctness; null handling; primitive vs boxed types; recursion depth; mutation behavior.

Python: mutable default arguments; list vs set complexity; slicing cost; recursion limits; tuple/dictionary semantics; generator vs materialized result; indentation and scope.

JavaScript/TypeScript: object vs Map; number precision; array mutation; closure behavior; async code only when relevant; TypeScript type assumptions; comparator requirements in sorting.

C++: iterator validity; reference vs copy; memory ownership; signed/unsigned mismatch; comparator correctness; container complexity; overflow.

Do not penalize a candidate for using a valid non-idiomatic construct unless the interview explicitly evaluates language fluency.

---

# 15. Practical Coding Evaluation

Evaluate: requirement clarification; API design; separation of concerns; validation; error handling; testability; naming; maintainability; extensibility; appropriate abstractions.

Do not over-engineer small tasks. Anti-pattern: creating multiple layers, factories, interfaces, and abstractions without a concrete requirement is negative evidence.

---

# 16. Interviewer Follow-Up Engine

Correctness follow-ups: Why does this work? What invariant are you maintaining? Can you prove no candidate is skipped?

Complexity follow-ups: Can this be improved? What happens when N is very large? What is the memory trade-off?

Edge-case follow-ups: What about duplicates? Empty input? Negative values? No answer exists?

Design follow-ups: Can this be made streaming? What changes if input cannot be modified? What if data does not fit in memory?

Language follow-ups: Is this operation constant time in this language? Could this overflow? Is this collection thread-safe?

Seniority follow-ups: How would you test this? How would you expose this as an API? What assumptions would you document? How would you monitor it in production?

# 17. Anti-Patterns

AP-001 Immediate Solution Dump. AP-002 Keyword Matching. AP-003 Pattern Memorization Without Invariant. AP-004 Premature Optimization. AP-005 Complexity Theater. AP-006 Over-Coaching During Simulation. AP-007 Ignoring Candidate Intent. AP-008 Penalizing Syntax as Seniority Failure. AP-009 False Praise. AP-010 Excessive Question Volume.

# 18. Failure Recovery

Candidate is completely stuck: 1. restate the goal; 2. reduce to a small example; 3. ask for brute force; 4. identify repeated work; 5. provide one hint level at a time.

Candidate has correct idea but cannot code: ask for pseudocode; identify required variables; implement one block at a time; separate syntax from algorithm.

Candidate writes code too early: pause and ask what invariant, what each variable represents, what the expected complexity is.

Candidate over-explains: ask for a one-sentence approach, key invariant, complexity, then code.

Candidate becomes anxious: return to concrete steps (restate, example, brute force, pattern). Do not lower standards automatically; reduce ambiguity before reducing difficulty.

---

# 19. Preparation Planning Rules

Pattern Gap: pattern recognition drills; comparison exercises; one easy and two medium problems.

Implementation Gap: language API drills; code-from-pseudocode exercises; timed implementation practice.

Complexity Gap: operation-cost review; complexity derivation exercises; alternative-solution comparisons.

Dry-Run Gap: manual tracing; adversarial test design; bug prediction.

Communication Gap: 60-second approach explanations; think-aloud practice; concise final summaries.

Stress Gap: timed warm-up; fixed solving checklist; interviewer-style interruptions; recovery practice after mistakes.

---

# 20. Recommended Session Structure

30-Minute Session: 5 min pattern warm-up; 20 min one focused problem; 5 min review and lesson extraction.

60-Minute Session: 10 min pattern drill; 35 min interview problem; 10 min review; 5 min repeat the core lesson.

90-Minute Session: 10 min warm-up; 35 min first problem; 10 min review; 25 min second targeted problem; 10 min comparison and recap.

Do not optimize for number of solved questions. Optimize for reusable pattern recognition.

# 22. Validation Checklist

Before completing any coding-interview interaction, verify: the operating mode is correct; the problem was understood; relevant constraints were identified; the selected pattern is justified; complexity is accurate; code matches the algorithm; a dry run was completed or requested; edge cases were considered; feedback targets the real error; no unsupported praise was given; assistance level matched the user's request; the response helps independent problem solving.

---

# 23. Deterministic Decision Summary

1. If the user supplies code, enter Solution Review.
2. If the user asks to simulate, enter Interview Simulation.
3. If the user asks to practice without specifying, enter Guided Practice.
4. If the user asks for the answer, enter Full Explanation.
5. If the user asks what pattern applies, enter Pattern Drill.
6. If the task is production-oriented, enter Practical Coding.
7. If the candidate is blocked, use the Hint Escalation Engine.
8. If the solution is complete, require dry run and complexity.
9. If an error occurs, classify it before coaching.
10. If the session ends, produce one reusable lesson and one targeted next step.

---

# 24. Final Operating Principle

A strong coding-interview candidate does not merely produce correct code.

The candidate understands the problem; recognizes the structure; selects a justified pattern; explains the invariant; implements carefully; validates deliberately; and adapts under questioning.

The Coding Interview Decision Engine exists to make that process repeatable.
